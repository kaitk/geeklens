# Processor catalogue sources and provenance

This document records where facts in the reviewed source and overlay modules under
[`src/catalogue/`](../src/catalogue/) come from, how their wording is chosen, and
how to re-verify a citation that has gone stale. It is the companion to
[geekbench7-sources.md](geekbench7-sources.md), which covers instruction-set
evidence rather than processor specifications.

Last reviewed: 2026-08-01. Every citation in the catalogue currently carries
`retrievedOn: '2026-08-01'`.

## What the catalogue asserts

Most of the catalogue is generated and carries no claims of its own:
`processorCatalogue.generated.ts` and `macCatalogue.generated.ts` hold identities
and chart averages captured from the Geekbench Browser, and are regenerated by
`scripts/generateProcessorCatalogue.ts` and `scripts/generateMacCatalogue.ts`.

Four kinds of fact are reviewed by hand, each carrying its own `CatalogueSource`:

| Field                          | States                                                    | Shown as                                               |
| ------------------------------ | --------------------------------------------------------- | ------------------------------------------------------ |
| `hardware`                     | Memory type, transfer rate, bus width, bandwidth          | Published memory facts beside the reported ones        |
| `coreComposition`              | The part's core groups and their counts                   | Named topology clusters, or a composition sentence     |
| `l3CacheDispute`               | That a reported L3 total cannot be believed               | A marked objection next to the reported value          |
| `SYSTEM_MEMORY_SPECIFICATIONS` | One exact system's memory, where the payload mislabels it | A published specification superseding the reported one |

Two rules make partial coverage safe, and should survive any edit here:

- **An absent entry renders exactly as the payload described it.** Nothing is
  inferred, so coverage can land in slices.
- **Only an exact identity match can state a published fact.** An alias or
  configuration mismatch resolves to unmatched and states nothing. Identity
  matching is exact string equality on normalized aliases: `Intel Core i9-13900K`
  resolves, and `Intel(R) Core(TM) i9-13900K` does not unless `REVIEWED_ALIASES`
  carries that form.

## Publisher tiers

`CatalogueSource.publisher` is a closed set: `Apple`, `Lenovo`, `Notebookcheck`,
`Qualcomm`, `Wikipedia`. It is closed so that adding a weaker class of source is
a deliberate edit rather than a passing choice.

Prefer the vendor's own newsroom, product page, or product brief. Fall back to
Wikipedia or Notebookcheck only where the vendor never published the fact — AMD
markets Strix Point as a flat core count, Apple never publishes memory type or
bus width, and Intel ARK serves 403 to automated retrieval.

The publisher is always visible to the user in the provenance tooltip, rather
than blended into a generic "published" attribution, so a Wikipedia-sourced
figure is never presented as though the vendor had stated it.

## How labels are worded

`CoreCompositionGroup.label` is recorded in the vendor's own wording and is never
normalized across vendors. This is a correctness rule, not a style preference:
Zen 5c is the same microarchitecture and IPC as Zen 5 at a lower clock, so filing
it under "efficiency" would state something false, and Intel's Low Power
Efficient-cores are not its Efficient-cores.

Within one vendor the wording is settled to the terms that vendor's current range
uses. Apple is the only range this applies to today: its older posts say
`high-performance`, `high-efficiency`, and `energy-efficient` for what its
current pages call performance and efficiency cores, and reproducing each
phrasing made rows differ where the silicon does not. `super` survives that
settling because it marks a real design boundary — see `APPLE_CORE_TIERS` in the
catalogue for what that costs, and
[tasks/apple-qualcomm-core-compositions.md](tasks/apple-qualcomm-core-compositions.md)
for the decisions taken when the Apple and Qualcomm ranges were added.

Group counts are nominal: they bound a reported cluster rather than equalling it,
because a result with cores disabled in firmware reports fewer than the part
ships. The matcher names clusters only when exactly one assignment is feasible,
so equal-count groups and single-group (homogeneous) parts correctly produce no
names.

## Retrieval notes

These are the hazards actually hit while building the catalogue. They cost real
time to rediscover.

- **Notebookcheck serves 403 to automated retrieval.** The M1 Pro citation was
  retrieved manually. Do not assume a Notebookcheck page can be re-checked by a
  script.
- **Intel ARK serves 403 to automated retrieval.** It lists P-core and E-core
  counts as separate fields, which would be the better source, but a page that
  cannot be retrieved must not be cited as though it had been.
- **The Geekbench Browser is behind a Cloudflare challenge** for automated
  fetches. Catalogue identities come from captured pages via the generator
  scripts, not from live requests.
- **Qualcomm product briefs are PDFs with no HTML equivalent.** Fetching one
  returns binary. The text lives in Flate-compressed content streams: inflate
  each `stream`/`endstream` range with `zlib.inflateSync`, then pull the
  parenthesised string literals. This recovers the full specification table for
  the X2 Elite, X Elite, and X Plus briefs.
- **The entry-level Snapdragon X brief carries its table as artwork**, so the
  same extraction yields headings and no values. That part's core count is cited
  to Wikipedia for this reason, and `qualcomm.com/products/…/snapdragon-x`
  404s.
- **Qualcomm's X Elite product page now leads with X2 marketing.** Reading X1
  tier claims off it produces the X2 split. Use the X1 briefs for X1 facts.
- **The former AnandTech M1 Pro citation 301-redirects** to an unrelated Tom's
  Hardware post that does not contain the claim. This is the precedent case for
  link rot below.
- **Do not accept a summarised page as a specification table.** A summarising
  fetch of the Snapdragon list article returned a confident, entirely fabricated
  "8 performance + 4 efficiency Kryo Gold/Silver" split for X1 parts. Quote the
  table, or read the raw wikitext via `?action=raw`.

## Re-verifying a citation

`retrievedOn` means: on this date, this URL was fetched and the page stated this
claim. It is not a "last edited" marker, and moving it forward without re-reading
the page defeats the only check the catalogue has.

To re-review a source:

1. Fetch the URL and confirm it still resolves without a cross-host redirect.
2. Confirm the page still states the specific claim — the count, the split, the
   bandwidth figure — not merely that it is about the right part.
3. Only then move `retrievedOn` forward.

When a link rots, do one of the following, in order of preference. Never keep the
claim and simply update the date.

1. **Replace it** with another source that states the same claim, preferring the
   vendor. Update the publisher if the tier changes.
2. **Downgrade it** to a weaker publisher and let the tooltip show that; a
   Wikipedia attribution the user can see is honest, a stale vendor URL is not.
3. **Delete the fact.** The entry then renders exactly as the payload described
   it, which is always a valid state.

There is deliberately no automated link checker. Three of the five publishers
block or challenge automated requests, so a checker would report failures for
pages that are perfectly healthy in a browser, and its green runs would mean
nothing. Re-review is a manual pass, and the shared `retrievedOn` date across the
catalogue is what makes an overdue one visible.

## Adding a source

Declare it as a module-level `CatalogueSource` constant named for the document,
not the part — `WIKIPEDIA_APPLE_M5_SOURCE`, `QUALCOMM_X1_PLUS_BRIEF_SOURCE` —
and reuse it across every entry it supports, so one re-review updates them all.
Where the choice of source is not obvious, comment why that page and not the
likelier one; the existing comments about AnandTech, Intel ARK, and the
unextractable Snapdragon X brief are the pattern.
